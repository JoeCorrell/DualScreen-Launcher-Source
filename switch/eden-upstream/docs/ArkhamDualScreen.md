# Batman: Arkham Asylum dual-screen companion

Reverse-engineering notes and implementation record for the `dualscreen` Android flavor's
Arkham Asylum companion. Everything below is traced from the user's own game files or from
the live process; anything not yet traced is marked as such rather than filled in with
plausible-looking values.

## Runtime access architecture

No fixed offsets into game structures. The companion walks UE3's own reflection data, so a game
patch that moves fields does not silently produce wrong numbers.

Resolution runs as a staged pipeline (`ResolveRuntime`), each stage validated before the next:

1. **GNames** — `main_base + 0x01C4BA70`, validated by requiring name index 0 to read as
   `"None"`. This is the one module-relative constant in the file.
2. **GObjects** — found by scanning for plausible `TArray` headers, then discovering the
   `Name`/`Class` field offsets by sampling objects (`DiscoverObjectLayout`).
3. **`RPersistentData`** class + live instance.
4. **Outer offset** — scored by counting properties whose Outer points at the known class.
5. **UProperty layout** — `property_base` and `property_value_member` scored against expected
   element sizes per property type.
6. Active.

The important consequence of stage 5: `property_base` describes the **UProperty layout in this
binary**, not any one class. Once pinned down from `RPersistentData` it applies to every
UProperty in GObjects, which is what makes generic per-class resolution possible for free.

### UProperty layout (corrected)

Measured values for this build:

| Item | Value |
| --- | --- |
| GObjects `Name` offset | `+0x38` |
| GObjects `Class` offset | `+0x40` |
| `Outer` offset | `+0x30` |
| `property_base` | `+0x68` |
| GObjects count (in-game) | ~92,000 |

At `property_base` the two words are:

```
property_base + 0x00 : ElementSize   (4 int/float, 8 FName/Object, 16 FString/Array)
property_base + 0x04 : Offset        (byte offset of the field within the object)
```

This corrects an earlier misreading. The original code treated the pair as
`{ArrayDim, ElementSize}` and took the field offset from `property_base + property_value_member`,
which held unrelated noise. A live `RInventoryGadget` dump settled it — its scalar fields
resolved to a contiguous 4-byte-spaced run while the supposed "element size" word was exactly
`sizeof` each property type:

```
MaxAmmo              IntProperty    size=4   offset=740
Ammo                 IntProperty    size=4   offset=744
CurrentRechargeTime  FloatProperty  size=4   offset=748
UpgradeLevel         IntProperty    size=4   offset=760
EquipBoneName        NameProperty   size=8   offset=712
TutorialText         StrProperty    size=16  offset=864
```

Every resolution is now gated on `MatchesElementSize`, so a candidate whose size disagrees with
its property type is rejected rather than accepted with a garbage offset.

**`ArrayDim` is not adjacent to this pair and has not been located.** Until it is, every property
is treated as scalar — a wrong dimension would make an array read walk off the end of the
object. The practical consequence is that `RPersistentData::UpgradesBought` currently yields one
entry instead of the full upgrade array, so the Skills page is not yet trustworthy.
`LogDiagnosticsOnce` dumps the raw UProperty words around `property_base` for one known static
array and one known scalar so the differing word can be identified next session.

### Why lookups are scoped by owning class

`Location`, `Health`, `MaxHealth` and `CurrentGadget` are each declared by dozens of unrelated
classes in `BmGame.xxx` (over 200 `ObjectProperty Controller` declarations alone). Resolving a
property by name globally would pick an arbitrary one. Every lookup therefore goes through
`ResolveClassProperties(class_object)`, which collects only UProperties whose Outer is that
class, and results are cached per class.

`Location`/`Rotation` resolve against `Actor` and `Health`/`HealthMax` against `Pawn`, because
`RPawnPlayerBm` does not redeclare them; the pawn class is still tried first so a Batman-specific
override would win.

### Live vs save state

`RPersistentData.PlayerLocation` / `PlayerRotation` / `PlayerHealth` are **save state** and only
advance at checkpoints. Reading position from there would leave the companion map frozen while
Batman is moving, which defeats the point of a live map.

Position, facing and current health are therefore read from the live `RPawnPlayerBm` instance,
with the persistent values kept only as a fallback for menus and loading screens where no pawn
exists (so the map holds the last known position instead of snapping to the origin).

Live objects are re-resolved on a cadence (every 8 polls, ~2 s at the companion's 250 ms poll)
because GObjects grows and the pawn is destroyed and re-created on every level load.
`FindInstanceOfClass` takes the **last** matching entry, since a reload appends a new pawn while
the stale one may not be cleared yet, and skips `Default__`/`Archetype` objects.

## Current state

Working and verified by compilation:

- Staged reflection discovery with fail-closed build guard.
- Save-state reads: XP curve, player level, story percentage, unlockable points, time played,
  `LocationID`, save chapter, upgrades-bought array, primary objective and description strings.
- Live pawn discovery, live position/facing, live health and a real `MaxHealth` denominator
  (`health_percent` was previously never computed because `max_health` was never written).
- Per-class property resolution with type-aware scalar reads (`MaxHealth` appears as both
  `IntProperty` and `FloatProperty` on different classes, so the type is read from the
  UProperty rather than assumed).
- Categorised logging under `[Arkham/Reflect]`, `[Arkham/Live]`, `[Arkham/Diag]`.

Deliberately **not** implemented, because it is not yet traced:

- **Gadget availability / unlock state.** `gadget_mask` currently reflects only the equipped
  gadget. Ownership of `RInventoryGadget` instances relative to `RInventoryManager` is unknown.
  `LogDiagnosticsOnce` dumps every gadget-named object with its class and Outer so a real
  session establishes the relationship.
- **Gadget selection write path.** There is no write path at all — `FillSnapshot` is the only
  exported entry point. Selection must go through the game's own functions
  (`UnequipAllOtherGadgets` / equip path), not by poking a field, and must be marshalled onto
  the game thread. MK8D's `ActivateItemSlot` is the model to follow.
- **Upgrade purchase.** Read-only. Must route through the real progression function.
- **Live map geometry.** No map assets extracted. `RGFxMovieMap` untraced.
- **Location names.** No name table traced; `LocationID` is forwarded as a number and the
  display name is left empty rather than fabricated as `"Location <n>"` (which the previous
  code did).
- **Localisation.** Objective/description strings come through as raw `FString`s; no
  language-aware path yet.

The Kotlin `GADGETS` and `SKILLS` arrays in `ArkhamCompanionView.kt` are still hardcoded from
outside knowledge and disagree with the traced set (8 entries vs 10, missing Detonator, Grapple
and Multi Batarang). They need replacing with the game's own strings.

## Snapshot frame

Fixed 480-byte little-endian struct, magic `ARKM` (`0x4D4B5241`), version 1, `static_assert`ed
in C++ and parsed by offset in Kotlin. **Changing the layout requires bumping `version` and
updating `ArkhamCompanionView.SNAPSHOT_SIZE` and its readers together.** The fields added in
this pass (`max_health`, `health_percent`) already existed in the struct and were simply never
populated, so no layout change was needed.
